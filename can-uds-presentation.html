Fundamentals

CAN is a broadcast bus that arbitrates on the fly

Every node hears every frame. There's no master — the frame with the lowest ID always wins the wire, non-destructively, mid-transmission.

  • Differential signaling: two wires, CAN_H / CAN_L. A dominant bit (logical 0) drives them apart; a recessive bit (logical 1) lets them float together. Dominant always wins a collision.
  • Multi-master: any node can start transmitting once the bus is idle (recessive) — there's no bus arbiter granting turns.
  • CSMA/CR arbitration: nodes transmit their ID bit-by-bit and simultaneously read the bus. The instant a node sends recessive but reads dominant, it lost — it backs off and retries later. Lower numeric ID = higher priority.
  • Non-destructive: unlike Ethernet's CSMA/CD, nobody's frame gets corrupted by the collision — the losing node just stops cleanly at the arbitration field.
Why this matters for diagnostics

UDS request/response traffic rides on top of this exact mechanism. A tester's diagnostic request is just another CAN frame competing for the bus — usually given a high-priority (numerically low) arbitration ID so it doesn't get starved behind high-rate sensor traffic.

Everything from here — frame layout, error handling, ISO-TP segmentation, UDS services — sits on top of this one arbitration rule.

Frame structure

Extended addressing — identical in Classical CAN and FD

One bit, IDE, decides everything. Its position on the wire never moves, whether the frame is Classical or FD — FD only adds fields after the identifier is already fully formed.

What IDE does
  • IDE = 0 (dominant): Standard frame. The 11 bits already sent are the whole identifier; DLC comes right after.
  • IDE = 1 (recessive): Extended frame. What looked like an 11-bit ID was only the base — 18 more identifier bits follow before DLC.
  • Because Standard's RTR and Extended's SRR occupy the exact same bit position, a Standard frame and an Extended frame that happen to share the same base 11 bits still arbitrate deterministically: RTR=0 (dominant, data frame) always beats SRR=1 (recessive) at that bit.
What changes on CAN FD — nothing, here

FD reuses the arbitration field byte-for-byte. FDF, BRS, ESI and the new DLC decode table all live strictly after IDE/SRR/RRS. A CAN FD 29-bit frame is formed by taking the Classical Extended arbitration field and appending the FD control bits — the ID logic itself is untouched. Frame structure → errors

Bit stuffing keeps every node's clock in sync

CAN has no separate clock wire — receivers resynchronize on every edge. A long run of identical bits would starve them of edges, so the transmitter inserts artificial ones.

The rule

After 5 consecutive bits of the same polarity (5 dominant or 5 recessive in a row), the transmitter inserts one bit of the opposite polarity. Every receiver knows the rule too, so it silently removes that bit before interpreting the data — it's invisible above this layer.

Stuffing applies from SOF through the end of the CRC field. EOF is deliberately exempt — its 7 recessive bits are how everyone agrees the frame just ended.

Why it doubles as error detection

If a receiver ever sees a 6th identical bit where stuffing should have broken the run, that's not noise it can shrug off — it's a guaranteed protocol violation. That's exactly the Stuff Error covered on the next slide.

CAN FD's extra safeguard

At FD's faster data-phase rate, mis-counting stuff bits during the CRC field would be more damaging (a single lost/gained bit could still pass a coincidentally-matching CRC on a long frame). So FD switches strategy inside the CRC field specifically:

  • Fixed stuff bits: instead of "after 5 identical bits," FD inserts one stuff bit every 4 bits through the CRC field, regardless of polarity.
  • Stuff count field: a 3-bit counter (plus parity) at the start of the CRC field tells the receiver exactly how many stuff bits it should have removed — a second, independent check on top of the CRC itself.

Net effect: FD's CRC field is more robust per bit than Classical's, which matters more as the data field — and therefore the CRC computation — got a lot longer.

Five ways a frame gets rejected — and what it costs the node

Every receiver polices every frame. The moment one of these five conditions is seen, the detecting node stomps an Error Frame onto the bus mid-transmission.

Active nodes send 6 dominant bits — this deliberately violates stuffing, so every other node also detects an error and joins in ("error contagion"), guaranteeing the whole bus agrees the frame is dead. Passive nodes send 6 recessive bits instead — quiet enough not to disturb a bus that's already fine, which is exactly the restraint an Error-Passive node is supposed to show. ISO-TP · ISO 15765-2

Flow Control — the receiver sets the pace

After the First Frame, the receiver is in charge of throttle: how many frames at a time, and how fast.

Flow Status (FS) values
FSMeaningSender does
0 CTSContinue To SendSends up to BS Consecutive Frames, STmin apart
1 WAITNot ready yetPauses — waits for another FC before sending any CF
2 OVFLWOverflow — can't buffer this messageAborts the transfer entirely (only legal after a First Frame)
Block Size (BS)

BS = N > 0: send exactly N Consecutive Frames, then stop and wait for the next FC. BS = 0: send the entire rest of the message uninterrupted. Tuned by the receiver to match its own buffering / interrupt latency.

ISO-TP · ISO 15765-2

CAN FD's Single Frame has two encodings

Classical CAN's 1-byte PCI tops out at 7 data bytes — the low nibble simply can't count higher. CAN FD needs a second, escaped encoding to use its full 62-byte SF capacity.

Two rules, one PCI type
  • Payload 1–7 bytes: use the same 1-byte PCI as Classical CAN — high nibble 0x0, low nibble = length. Works identically whether the physical frame is Classical or FD.
  • Payload 8–62 bytes: the low nibble can't hold a value >7, so it's fixed at 0x0 too — making byte 0 the literal escape value 0x00 — and a whole second byte carries the real length, SF_DL, 1–62.
  • 62 is the hard ceiling: a 64-byte FD frame minus the 2-byte escape PCI leaves 62 bytes for data — no more.
  • First Frame and Consecutive Frame PCI sizes don't change on FD — FF is always 2 bytes of PCI, CF is always 1 — only the Single Frame gets this extra rule, because it's the only type where "does it all fit in one frame" is even a question.
Practical note

CAN FD only has 8 legal physical frame sizes (see the DLC table). A 20-byte SF payload needs 22 bytes on the wire (2 PCI + 20 data) — there's no 22-byte FD frame, so it goes out as a 24-byte frame with 2 bytes of padding, typically 0xCC or 0xAA depending on the tool/OEM convention.

UDS · ISO 14229-1

Every UDS exchange is one of three shapes

UDS rides as the payload of an ISO-TP message (Single Frame or segmented) — everything below is what's inside that payload.

# Request — client → ECU
SID  [SubFunction]  [Parameter...]

# Positive response — SID + 0x40
SID+0x40  [SubFunction]  [Data...]

# Negative response — fixed 3-byte shape
0x7F  SID  NRC
Suppress positive response — the short version

Only services that carry a SubFunction byte can suppress their positive response, by setting bit 7 (0x80) of that byte. Example: 10 03 (Extended Session, normal) vs 10 83 (same request, "don't bother replying if it worked"). A negative response is never suppressed — if something's wrong, the client always hears about it. Full supported-service list on the Suppressed Response slide.

Physical vs. functional addressing
PhysicalFunctional
TargetsOne specific ECUEvery ECU listening on that functional ID
Typical arb. ID pattern0x7E0–0x7E7 style, one per ECUA shared broadcast ID, e.g. 0x7DF

Common useFlashing, security access, DID read/write — anything ECU-specificBroadcasting 10 03 or 3E 00 to wake up a whole network at once

A tester tool almost always uses physical addressing for the actual flash sequence (0x27/0x34/0x36/0x37 must go to one ECU), and reserves functional addressing for broadcast conveniences like putting the whole vehicle into a diagnostic session together.

UDS · ISO 14229-1

Sessions gate which services are even legal

Almost every service on the next slides checks "am I in the right session?" before doing anything else — this is the state machine underneath that check.

The three common sessions
01 · Default
⇄
03 · Extended
⇄
02 · Programming
SessionWhat's normally allowed
01 DefaultThe power-on state. Read-mostly: 0x22, 0x19. Reprogramming and most security-gated writes are blocked here.
03 ExtendedUnlocks routine control, most 0x2E writes, and is the usual prerequisite for requesting 0x27 security access.
02 ProgrammingWhere 0x34/0x36/0x37 flashing actually happens — reachable only after security access, and it deliberately disables most other services (the ECU is busy).
Falling back to Default

Every non-default session runs an S3 timer (commonly ~5 s). If the client doesn't send something diagnostic before it expires — normally a 0x3E TesterPresent keep-alive — the ECU silently drops back to the Default session on its own.

Why this matters mid-flash

Losing Programming session mid-transfer (S3 timeout, a reset, a dropped tester-present) invalidates the whole 0x34/0x36 sequence — the ECU expects to restart from 0x34. This is exactly why flashing tools hammer TesterPresent throughout the entire OTA sequence.

UDS service · shared across OEMs (except the algorithm)

0x27 SecurityAccess

A two-message handshake: request a seed, compute a key, send the key back. The handshake shape is universal — the math that turns seed into key is the one thing every OEM keeps proprietary.

# Odd subfn = request seed
27 01
67 01  A4 7C 91 02  ; 4-byte seed

# Even subfn = send computed key
27 02  9F 10 3B 5C
67 02  ; key accepted, no payload needed

# Seed of all-zero = already unlocked, key step skippable

Odd levels (0x01, 0x03, 0x05…) request a seed; the next even level (0x02, 0x04, 0x06…) submits the key for that same level. Higher levels are typically gated behind lower ones and/or the Programming session.

Relevant NRCs
0x24 requestSequenceError 0x31 invalid level 0x33 securityAccessDenied 0x35 invalidKey 0x36 exceedNumberOfAttempts (auto) 0x37 requiredTimeDelayNotExpired (auto)
Suppress positive response

Not supported — explicitly excluded by ISO 14229-1. The client needs the seed to compute a key, so suppressing the seed response would break the protocol.

What's shared vs. proprietary

Shared: odd/even level convention, seed-then-key ordering, and the attempt-counter/delay-timer state machine (0x36 → start a delay → 0x37 until it expires) are identical everywhere. Never shared: the actual seed→key transform — XOR tables, AES, custom ciphers — it's supplier IP by design, and this deck won't guess at any real one.

The write-side twin of 0x22 — same DID addressing, now carrying data inbound instead of outbound.

0x34 RequestDownload

"I'm about to send you N bytes starting at address A — how big can each chunk be?" The ECU's answer here shapes every TransferData request that follows.

# dataFormatId=00 (uncompressed/unencrypted), addr&lenFmt=44,
# 4-byte address 0x08010000, 4-byte size 0x00040000 (256KB)
34 00 44  08 01 00 00  00 04 00 00
# lengthFormatId=02 (2 length-bytes follow), maxBlockLength=0x1000

  • dataFormatIdentifier — high nibble = compression method, low nibble = encryption method (0x00 = neither).
  • addressAndLengthFormatIdentifier — high nibble = byte-length of the size field, low nibble = byte-length of the address field.
  • maxNumberOfBlockLength — the ceiling for every subsequent 0x36 request's total message size, including the 2-byte 0x36/BSC overhead.

  • 27 01 / 27 02 → Security access unlock
  • 31 01 FF00 → checkProgrammingDependencies (pre-check)
  • 10 02 → Programming session
  • 34 → RequestDownload, learn maxNumberOfBlockLength
  • 36 × N → TransferData, one BSC per block, each block itself multi-frame
  • 37 → RequestTransferExit, verify checksum/signature
  • 31 01 FF00 → checkProgrammingDependencies (post-check)
  • 2E F184 / F199 → write fingerprint + programming date
  • 11 01 → hard reset into the new image
  • 19 0A / 22 F186 → confirm no new DTCs, confirm active session/version

3E 00 TesterPresent runs throughout, off the critical path, to hold the session open.

Timing

P2, P2*, and the difference between "slow" and "silent"

Three shapes the wait for a response can take. Only two of them are the same failure mode.

P2server_max

Default per-request timeout, commonly ~50ms. Returned by the ECU in the 0x10 response.

P2*server_max

Extended timeout after a 0x78, commonly up to ~5s. Also returned by the ECU in the 0x10 response.

S3_Client

How long a non-default session survives with no traffic at all — see the Session Model slide. Kept alive with 0x3E.

Cross-OEM behavior

The byte layout is standard. The policy is not.

ISO 14229-1 fixes the wire format for every OEM. What each OEM decides independently is when a service is allowed and what its parameters mean.

ServiceIdentical on every OEMOEM/supplier-specific
0x10SubFunctions 01/02/03, request/response byte shapeActual P2/P2* values; extra sessions in 0x40–0x5F
0x11SubFunctions 01–05, request/response byte shapeWhich resets are allowed from which session; pre-reset routine gating
0x22Byte layout; meaning of DIDs 0xF180–0xF19FEverything in 0xF1A0+ and most of 0x0100–0xF0FF
0x2EByte layoutWhich DIDs are writable, from which session/security level
0x27Odd/even level convention; attempt-counter & delay-timer state machine (0x36/0x37 NRCs)The seed→key algorithm itself — always proprietary, by design, never standardized

This is exactly why a generic diagnostic stack can implement session control, reset, and DID read/write once and reuse it across OEMs — but security access always needs an OEM/supplier-specific plugin.
