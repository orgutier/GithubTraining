Fundamentals · absolute basics

What is Python, and how does code run?

Zero prior coding experience assumed here. If you've never written a line of code before, start exactly on this slide.

Theory
An interpreted, general-purpose language

Python is a programming language: a precise, written way to tell a computer exactly what to do. It's interpreted, not compiled — there's no separate "build" step that turns your code into a program first. Python reads your file and runs it, one line at a time, top to bottom. It's used for automation scripts, web servers, data analysis, and — what we're here for — testing and API work.

Theory
A program is just a text file

A Python program is plain text saved in a file ending in .py — for example hello.py. You write it in any text editor. Nothing happens until you tell your computer to run it with the python program installed on your machine (sometimes called python3).

Code
$ python3 hello.pyi
Hello, World!

This is the terminal (also called a shell or command line) — a text-only way to run programs. $ is just the prompt showing it's waiting for a command; you don't type it yourself.

Theory
Bonus: the interactive REPL

Typing plain python3 with no file opens the REPL (Read-Eval-Print Loop) — an interactive prompt (>>>) where you type one line, see its result immediately, and keep going. Great for quick experiments; not how real programs are saved and shared — that's what .py files are for.

Practical exerciseJunior6 min

Do this: open a terminal and run python3 --version (or python --version) to confirm Python is installed. Then create a file named warmup.py containing print("I can run Python"), save it, and run it with python3 warmup.py.

Fundamentals · absolute basics

The syntax rules every Python file follows

Four small rules that explain almost every red squiggly line you'll see as a beginner.

Theory
Indentation is not optional

Many languages group code with { } braces. Python uses indentation (whitespace at the start of a line) instead — consistently 4 spaces per level, by convention. Everything indented under a line ending in : belongs to it. Get the indentation wrong and Python raises an IndentationError instead of running.

Code
if 5 > 3:i
print("5 is bigger") # indented — inside the ifi
print("this always runs") # not indented — outside the ifi
Theory
Three more rules
  • A line ending in : always opens an indented block — if, for, while, def, class, try all work this way.
  • Python is case-sensitive: name, Name, and NAME are three different variables.
  • Variable and function names conventionally use snake_case (lowercase, words separated by underscores) — user_name, not userName.
Practical exerciseJunior7 min

Do this: type the correctly-indented example above into a file and run it. Then deliberately remove the 4-space indent from the print("5 is bigger") line, run it again, and read the IndentationError Python shows you — that error message is your friend, not something to fear.

Fundamentals

Variables are labels, not boxes

A variable is a name you attach to a value so you can use it again later. Python is dynamically typed: a name can be rebound to a value of a different type at any time.

Code
name = "Ada Lovelace"i
age = 36i
gpa = 3.9i
is_hired = Truei
manager = Nonei
Code
age = "thirty-six" # same name, new type — legali
print(type(age))i
<class 'str'>
Theory
What to know
  • Strong, dynamic typing: Python checks types at runtime, not compile time — but it never silently coerces "3" + 3.
  • Immutable core types: str, int, float, bool, tuple can't change in place — every "modification" makes a new object.
  • Mutable core types: list, dict, set change in place, which matters once you share them between functions or tests.
  • Type hints (age: int) document intent for tools like mypy — Python still won't enforce them at runtime on its own.

Fundamentals

Conditionals: if / elif / else

How a program makes decisions — run one block of code or another, depending on whether something is true.

Theory
Every condition reduces to True or False

The expression after if is evaluated, and Python asks: is this truthy or falsy? 0, 0.0, "" (empty string), None, and empty containers ([], {}) are all falsy. Virtually everything else — including any non-zero number or non-empty string — is truthy.

Code
score = 82i
if score >= 90:i
grade = "A"i
elif score >= 80:i
grade = "B"i
else:i
grade = "C or below"i
print(grade)i
B

Python checks each condition top to bottom and runs only the first block that matches — elif ("else if") is only reached if every condition above it was False. else catches everything else, with no condition of its own.

Loops: for & while

How a program repeats itself — running the same block of code once per item, or until a condition changes.

Theory
Two ways to repeat

for repeats once per item in something iterable — a list, a string, or a count from the built-in range(n) (which produces 0, 1, 2, … n-1). while repeats for as long as a condition stays True — more flexible, but riskier: forget to change the condition, and you get an infinite loop. break exits a loop immediately; continue skips straight to the next iteration.

Code

for color in colors:i
print(color)i
red green blue
Code
count = 0i
while count < 3:i
print("tick", count)i
count = count + 1 # without this line, the loop never endsi
Code
for n in range(10):i
if n == 5:i
break # stop the loop entirelyi
if n % 2 == 0:i
continue # skip the rest of this iterationi
print(n)i
1 3

Functions: def, parameters & return

A function packages a piece of logic under a name, so you can reuse it instead of copy-pasting.

Theory

A function is defined once with def, a name, and a set of parameters (the inputs it accepts) — then called as many times as you like with different arguments (the actual values passed in). return sends a value back to whoever called it; without a return, a function silently produces None.

Scope & *args / **kwargs

Where a function's variables live, and how to accept a flexible number of arguments — the exact shape that makes decorators and pytest fixtures possible later in this deck.

Code

Theory
Scope in one paragraph

Python looks up a name Local → Enclosing → Global → Built-in (LEGB). A name assigned inside a function is local to it by default — nothing leaks out, unless you explicitly return it.

Errors & exceptions

Exceptions are Python's control flow for "something went wrong." Handling them precisely — not with a bare except: — is exactly what a good test suite exercises.

Theory
What an unhandled error looks like

When Python hits an error it doesn't catch, it prints a traceback and stops. Read it from the bottom up: the last line is the exception type and message — the actual problem. The lines above it are the call stack, showing exactly which line triggered it.

@dataclass is the fast path to a clean, comparable data object — exactly the shape you'll want for API request/response models and test fixtures.

Pythonic & OOP

Context managers & the with statement

Anything that needs guaranteed cleanup — a network session, a file, a temporary resource in a test — belongs in a context manager, not a manual try/finally you might forget.

Code
class ApiSession:i
def __enter__(self):i
self.session = requests.Session()i
return self.sessioni
def __exit__(self, exc_type, exc, tb):i
self.session.close()i
with ApiSession() as session:i
response = session.get("https://api.example.com/health")i
Theory
The two dunder methods
  • __enter__(self) runs when the with block starts; whatever it returns becomes the as variable.
  • __exit__(self, exc_type, exc, tb) runs when the block ends — even if it raised — and receives the exception details, if any.
  • Same idea as a finally block, but scoped to exactly one resource and reusable across every place that needs it.
Practical exerciseMid10 min

Testing fundamentals

Why we test, and at what level

Not every check belongs at the same altitude. The testing pyramid is a budget: lots of cheap, fast unit tests; fewer integration tests; a thin layer of slow, high-confidence end-to-end tests.

Advanced testing

Mocking & patching with unittest.mock

Unit tests shouldn't make real network calls. patch swaps a real object for a fake one for the duration of a test, so you can assert on how your code used it.

Code
from unittest.mock import patchi
@patch("mymodule.requests.get")i
def test_fetch_user_calls_api(mock_get):i
mock_get.return_value.status_code = 200i
mock_get.return_value.json.return_value = {"id": 1, "name": "Ada"}i
user = fetch_user(1)i
mock_get.assert_called_once_with("https://api.example.com/users/1")i
assert user["name"] == "Ada"i
Theory
Mental model
  • @patch("mymodule.requests.get") patches the name requests.get as imported into mymodule — patch where it's used, not where it's defined.
  • The mock is injected as the first extra argument (mock_get) — it's a stand-in you fully control.
  • .return_value configures what calling the mock produces; assert_called_once_with(...) verifies exactly how your code called it.

Coverage is a floor, not a target

pytest-cov tells you what ran. It cannot tell you whether what ran was actually verified.

Theory
What coverage can't see
  • Line coverage only proves a line executed — a test with zero assertions can hit 100%.

What to know

Sessions, auth & handling failure

Production code — and realistic tests — reuse a Session and handle the network failing, because it will.

Code

Theory
Why a Session

A plain requests.get() opens a new TCP connection every time. requests.Session() reuses connections and lets you set shared headers (like auth) once instead of on every call — closer to how a real client behaves.

Testing APIs

Mocking HTTP calls with responses

When your code calls an external API, don't call the real thing in a unit test. The responses library intercepts requests calls at the network layer and hands back exactly what you script.

Code
import responsesi
@responses.activatei
def test_get_active_users():i
responses.add(i
responses.GET, "https://api.example.com/users",
json=[{"id": 1, "name": "Ada", "active": True}], status=200,
)
users = get_active_users("https://api.example.com")i
assert users[0]["name"] == "Ada"i
Theory
Why not unittest.mock here?

You could patch requests.get directly, but responses operates one layer lower — at the actual HTTP adapter — so your code's real call construction (URL, params, headers) is exercised and can be asserted on, while the socket itself never opens.

pytest in CI

The same command you run locally should run in CI — no separate "CI-only" test logic. GitHub Actions just calls pytest in a clean environment, every push.

Code

Theory
Reading the flags
  • --maxfail=1 stops the run at the first failure — fast feedback in CI, where you'll re-run locally with full detail anyway.
  • -q keeps CI logs short; use -v locally while debugging a specific failure.
  • --cov-fail-under=85 fails the build outright if coverage regresses below the agreed floor.
