Fundamentals

Git thinks in snapshots, not diffs

Every commit is a full picture of your project at that moment. Git figures out differences later, on demand — it doesn't store them.

  • Distributed: every clone has the entire history. There's no central server required to commit, branch, or view history.
  • Local first: almost everything you do — staging, committing, branching, stashing — happens on your machine, offline, instantly.
  • Content-addressed: every commit, file blob and tree is identified by the SHA-1/SHA-256 hash of its content, not a filename.
  • GitHub is optional: it's a hosting service for one particular remote called origin — Git itself doesn't know GitHub exists.

Fundamentals

git init — where does history actually live?

A repository is just a hidden folder. There is no database, no server, no daemon — just objects and pointers on disk.

shell — ~/app
$git init
Initialized empty Git repository in ~/app/.git/
$find .git -maxdepth 1
.git/HEAD .git/config .git/refs/ # branch & tag pointers .git/objects/ # every blob, tree & commit, by hash .git/index # the staging area, as a file
$cat .git/HEAD
ref: refs/heads/main
The pieces that matter
  • HEAD — a pointer to "where you are right now." Usually it points at a branch, not a commit directly.
  • refs/heads/* — one file per local branch, each holding the hash of its latest commit. A branch is a 41-byte pointer.
  • objects/ — a content-addressed store: blobs (file contents), trees (folder listings) and commits, each named by hash.
  • index — the staging area. git add writes to it; git commit reads from it.
Good to know

git init only ever creates local state. Nothing is sent anywhere. GitHub only enters once you add a remote — later in this deck.

Core loop

git restore — undo one file, precisely

Two different undos, one command: unstage a file without touching its edits, or discard the edits entirely. Neither ever moves HEAD or a branch — that's what makes it safer than reset.

Core loop

git reset — undo a commit, three ways

Unlike restore, reset moves HEAD and the current branch pointer. The flag decides how much else it touches: just history (--soft), history and staging (--mixed, the default), or everything (--hard).

Branching

A branch is a movable pointer, nothing more

git branch creates a new pointer at the current commit. git switch -c (or the older git checkout -b) creates it and moves HEAD there in one step.

Stash

Stash — a shelf beside the workspace

Need to switch branches with unfinished changes? git stash tucks your edits onto a stack without a commit. git stash pop brings them back.

Merge · 1 of 2

Fast-forward merge — just slide the pointer

If main hasn't moved since you branched, merging needs no new commit at all — Git just moves the main pointer forward to your branch tip.

Merge · 2 of 2

Three-way merge — a commit with two parents

If both branches moved forward, Git compares base, ours and theirs, then creates a new merge commit that ties both histories together. Nothing is rewritten — every original commit is preserved.

Rebase

Rebase — replay commits on a new base

git rebase main takes your branch's commits, sets them aside, and re-applies each one, in order, on top of the latest main. Same changes, brand-new commit hashes, straight-line history.

Choosing a strategy

Merge vs. rebase — same content, different history

Neither is "correct." They optimize for different things — pick per-team, or even per-branch.

git merge
History shapeBranching, true-to-life

Conflict exposureOnce, all at once
Safe on shared/pushed branches?Always
Extra noiseOne merge commit
git rebase

Rule of thumb: rebase your own local, not-yet-pushed feature branch to keep history tidy before opening a pull request. Merge (never rebase) once a branch is shared, public, or already pushed — rewriting shared history breaks everyone else's clone.

Squash · 1 of 2

git merge --squash — many commits, one arrival

All of a branch's changes are combined into a single new commit on the target branch. The branch's own commit history is not attached — only the resulting file changes are.

Squash · 2 of 2

git rebase -i — squash before you even merge

Interactive rebase lets you rewrite your own branch's history: reorder, reword, or squash/fixup commits into each other — before anyone else ever sees them.

Squash · deep dive

Two roads to one commit — squash before vs. squash as part of the merge

Both end with a single tidy commit on the target branch. They differ in when the squashing happens and who controls it.

Squash before merge — git rebase -i
WhenOn your own branch, any time before the PR merges — often right before requesting review
Who runs itYou, the branch owner, locally
What gets rewrittenYour feature branch's own commits get new hashes
Force-push needed?Yes, if the branch was already pushed
ControlFine-grained — pick exactly which commits fold together, reorder, reword each one
Target branch (main)Untouched until the eventual merge/PR
Squash as part of merge — git merge --squash
WhenExactly at merge time — this is the merge step
Who runs itWhoever merges — often automated by GitHub's "Squash and merge" button
What gets rewrittenNothing on the feature branch; main simply gains one new commit
Force-push needed?No — the feature branch itself never changes
ControlCoarse — every commit on the branch folds into exactly one, no in-between shaping
Target branch (main)Gains one new commit; feature branch is usually deleted right after

They compose. Plenty of teams do both: interactive rebase locally to turn 15 "wip" commits into 2-3 meaningful ones for a cleaner review, then still let GitHub's "Squash and merge" collapse those into a single commit on main — because the team's policy is "one commit per feature," full stop, regardless of how any individual author likes to work. If you already rebase-squash to perfection, a regular merge (not squash-merge) at PR time preserves that curated history instead of flattening it further.

Conflicts

A conflict is just two answers to the same question

Git can auto-combine changes to different lines. When both sides touch the same lines and Git can't tell which should win, it stops and asks you.

  • Git pauses the operation (merge, rebase, cherry-pick, pull) and writes conflict markers directly into the file.
  • The working tree shows both versions at once — it's on you to decide (or blend) which lines survive.
  • Once you edit the file to its final form, git add tells Git "this is resolved" — staging a conflicted file means resolved, not just "attempted."
  • Every conflicted operation offers the same escape hatch: --abort puts everything back exactly as it was.
config.py — working tree
<<<<<<< HEAD
TIMEOUT_SECONDS = 30
=======
TIMEOUT_SECONDS = 60
>>>>>>> feature/longer-timeout

Everything above the ======= is HEAD — your current branch. Everything below is the incoming change. Delete the markers, keep whichever lines (or combination) is correct, save, then stage the file.

Conflicts in a merge

One conflict, resolved once, one commit

A merge compares the two branch tips against their common ancestor in a single pass. If anything overlaps, the whole merge pauses until it's resolved.

Conflicts in a rebase

Rebase can conflict — repeatedly, one commit at a time

Because each commit is replayed individually, a rebase can pause on commit 2 of 3, get resolved, then pause again on commit 3. --continue moves to the next; --skip drops the current one; --abort undoes everything.

Cherry-pick · 1 of 2

git cherry-pick — copy exactly one commit

Take a single commit from anywhere and replay it onto your current branch as a brand-new commit. The original commit is untouched and stays right where it was.

Cherry-pick · 2 of 2

Cherry-pick conflicts work just like rebase

If release has since changed the same lines hotfix touches, the pick pauses. Resolve, git add, then git cherry-pick --continue — or --abort to bail out entirely.

Beyond cherry-pick

Just want one file from another branch? Skip the commit entirely

Cherry-pick copies a whole commit. git restore --source copies just a file's content from anywhere — no switch, no merge, no new commit, nothing for the graph to even show.

Local → Remote

fetch, pull and push — moving commits across the wire

The remote is just another repository — usually hosted on GitHub. origin/main is a local bookmark for "where I last saw their main."

Local → Remote

Fast-forward or rebase? It depends on who moved

Neither is the default answer. Which one applies depends entirely on whether your branch has commits of its own since the last time you synced.

Only origin moved

Nobody committed locally since the last sync — there's nothing of yours to preserve.

  • Fast-forward is always possible: Git just slides your branch pointer up to match.
  • A plain git pull (or git merge origin/main) does it — no flag, no new commit, nothing to decide.
  • --rebase here would still "work," but there's nothing to replay — it's a no-op dressed up as a decision.
Both sides moved — diverged

You have local commits and origin has commits you don't — a fast-forward is impossible.

  • Merge (git pull, no flag): ties both histories together with a two-parent merge commit. Nothing rewritten.
  • Rebase (git pull --rebase): replays your commits on top of origin's — linear history, but new hashes for every one of yours.
  • Rebase only if those commits are yours alone — never rebase commits someone else has already based work on.
The rule

git fetch never changes your branch — it only updates origin/main. That makes it always safe to look before deciding. The next slide shows exactly which commands tell you which situation you're in.

Local → Remote

After git fetch, how do you actually know?

git fetch alone never changes your branch — so it's always safe to check first. git status and git log answer it directly, no guessing.

GitHub

From a pushed branch to a merged pull request

Everything before this slide happened with plain git. GitHub adds a review layer on top of the exact same objects and refs.

  • git push -u origin feature/pagination uploads your commits and creates the remote branch.
  • GitHub offers to open a Pull Request: a diff of feature/pagination against main, plus a place for comments and CI checks.
  • Reviewers comment inline; you push more commits to the same branch — the PR updates automatically.
  • When it's approved, you choose the merge strategy — and now you already know exactly what each one does to history.

Resolving it — same skills, familiar commands
  • Locally: git checkout feature/pagination → git pull origin main (or git merge main) — the exact merge conflict from earlier slides appears in your editor.
  • Resolve the markers, git add, git commit, then git push — the PR updates and the block clears.
  • Or use GitHub's web-based conflict editor for small, single-file conflicts — same markers, same rule: keep what's correct, delete the markers.
  • A rebase-heavy team may instead run git pull --rebase origin main locally to keep the branch linear before pushing.
